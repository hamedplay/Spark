# Spark Installation Air-Gapped

Spark Manager supports a separate **Installation Air-Gapped** workflow for environments that cannot reach Docker Hub, `download.docker.com`, npm, GitHub, or other public package registries during deployment.

The normal online Installation menu is unchanged. Air-gapped mode uses a versioned, checksum-verified bundle built on a connected staging host and imported into the target server.

## What the bundle contains

A generated bundle contains the complete install-time payload for the selected Ubuntu release and `amd64` architecture:

- Spark source as a Git bundle at an exact commit.
- Official Supabase `master` source as a Git bundle at an exact commit.
- Ubuntu base packages plus Docker CE, Docker Compose/Buildx, Node 24, Nginx, Certbot and Coturn as local `.deb` files.
- npm 11 package and the frontend `node_modules` tree generated by `npm ci`.
- Every Supabase Docker image referenced by the official Compose snapshot.
- A prebuilt Avatar Worker image, so its Dockerfile does not need npm access on the target.
- LiveKit, Redis, Egress, Ingress, MinIO and all LiveKit observability images.
- Optional Spark `manager.conf`.
- Optional TLS certificate/private-key pack for a fully disconnected installation.
- `manifest.json`, `metadata/manifest.env`, per-file `SHA256SUMS`, and an outer archive SHA256 file.

The target does not run `git pull`, `docker pull`, `docker build`, `npm ci` against the Internet, Docker APT repository setup, NodeSource setup, or ACME issuance while the air-gapped installer is active.

## Build the bundle on a connected staging host

The staging host must have the Spark repository at `/opt/spark`, Docker, npm and Internet access to all package/image registries required by Spark.

Open:

```text
spark
→ Installation Air-Gapped
→ 01 Build complete offline bundle
```

The builder asks for the target Ubuntu release (`24.04` or `26.04`), an output directory, and an optional TLS certificate source.

The result is similar to:

```text
spark-airgap-<spark-commit>-ubuntu26.04-amd64-<timestamp>.tar.gz
spark-airgap-<...>.tar.gz.sha256
```

### TLS certificate pack

A completely disconnected run of all installation steps requires certificates because normal steps 13 and 19 use public ACME/Let's Encrypt.

Provide either:

```text
/path/to/cert-pack/
  shahrmeeting.ir/
    fullchain.pem
    privkey.pem
  api.shahrmeeting.ir/
    fullchain.pem
    privkey.pem
  turn.shahrmeeting.ir/
    fullchain.pem
    privkey.pem
  meet.shahrmeeting.ir/
    fullchain.pem
    privkey.pem
  ingress.shahrmeeting.ir/
    fullchain.pem
    privkey.pem
```

The main application certificate must also contain the configured `www` domain in its SAN list.

Alternatively, when the staging host already owns the Spark Certbot tree and `/etc/spark/manager.conf`, `/etc/letsencrypt` can be selected. Only certificates for the exact Spark domains are copied into the bundle; unrelated keys are not exported.

If certificates are omitted, the bundle is still usable for package/source/image/npm preparation, but **Run complete offline installation** refuses to claim a complete installation and reports the missing TLS pack.

## Transfer to the isolated target

Transfer the bundle using the bank-approved mechanism (file gateway, removable media, SFTP/SSH, etc.). Verify the outer checksum if the `.sha256` file accompanies the archive:

```bash
sha256sum -c spark-airgap-*.tar.gz.sha256
```

## Bootstrap a fresh target with no Internet

From the transferred Spark repository, run:

```bash
sudo bash deploy/spark-cli/bootstrap-airgap.sh /path/to/spark-airgap-....tar.gz
```

The bootstrap process:

1. validates all bundle SHA256 hashes;
2. validates Ubuntu release and architecture;
3. installs all `.deb` packages from the local bundle with external APT sources disabled;
4. restores the exact Spark commit from the local Git bundle;
5. installs Spark Manager and the Air-Gap backend locally;
6. imports and verifies every Docker image from the bundle;
7. activates the imported bundle under `/opt/spark-airgap/current`.

After bootstrap:

```text
spark
→ Installation Air-Gapped
```

Use **05 Run complete offline installation** for a complete guided installation, or **04 Run one offline install step** for controlled troubleshooting.

## Air-gapped execution model

When an offline install step runs, Spark sets `SPARK_AIRGAP_ACTIVE=1` only for that task. The standard installation functions remain the source of truth, but network-dependent operations are replaced or intercepted in a narrow scope:

- Step 02 installs local `.deb` packages and local npm 11.
- Step 03 restores Spark from `spark.git.bundle`.
- Step 04 restores Supabase from `supabase.git.bundle`.
- Step 10 uses verified local Docker images, replaces Avatar Worker's build definition with the prebuilt image, and skips Compose pull/build.
- Step 11 restores the verified frontend `node_modules` payload before the normal production build.
- Step 13 imports and validates TLS certificates instead of ACME issuance.
- Step 17 disables online Certbot renewal/dry-run and records the offline renewal policy.
- Step 19 imports LiveKit/Ingress certificates rather than requesting them.
- Steps 20 and 22 use only bundled LiveKit/observability images; Compose pull is disabled in the air-gap task scope.
- LiveKit public TLS validation is redirected through loopback while preserving the correct TLS SNI/domain checks.

All remaining installation logic, security hardening, migrations, service readiness checks, firewall rules and deployment validation continue to use the existing production installer.

## Certificate renewal in an isolated environment

Automatic Let's Encrypt renewal cannot work without ACME network access. In Air-Gapped mode the Certbot timer is intentionally disabled. Renew certificates externally, create a new approved certificate pack/bundle, import it, and rerun the relevant certificate steps before expiry.

## Audit properties

Each bundle records:

- Spark commit SHA;
- Supabase commit SHA and branch;
- target Ubuntu release and architecture;
- prebuilt Avatar Worker image tag;
- creation timestamp;
- whether configuration and certificate packs are included;
- SHA256 for every internal artifact.

Docker image names and image IDs are also recorded under `docker/` so the transferred runtime can be reviewed before deployment.

## What still must exist on the isolated production network

Air-gapped mode removes **artifact-download** dependencies; it does not bypass the production network model. The configured Spark/LiveKit DNS names must still resolve as required by the normal installer, local services must be able to reach each other, and the production ingress/TURN ports must be routed according to the deployment architecture. External providers used by the application at runtime (for example SMS or other explicitly configured integrations) remain separate runtime dependencies and are not embedded into the installation bundle.
